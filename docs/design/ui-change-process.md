# UI 变更流程：先交互稿，评审通过，再改代码

任何改变用户可见界面的工作（布局、层级、组件结构、新增/删除入口、状态与文案），
都按本文的顺序推进。**没通过评审的交互稿，不进前端代码。**

目的很直接：UI 的返工成本几乎全在写完代码之后。文字表述读不出「挤不挤」「看不看得懂」，
一旦落地成 `tsx` 才讨论，改动就变成删代码 + 重排组件 + 补测试；而在交互稿阶段改一个
区块的位置，成本接近零。

## 1. 先出交互稿

交付物放在 `docs/design/changes/<slug>/`（该目录按需新建），至少包含：

| 文件 | 内容 |
|---|---|
| `README.md` | 目标、受影响的路由/视图、状态清单、与现状的差异点、待决问题 |
| `screen-*.jpg\|png` | 每个**状态**一张图，文件名写清状态（`01-empty.jpg`、`02-loading.jpg`、`03-error.jpg`） |
| `flow.md` | 只在多步交互时写：进入条件、关键操作序列、返回/取消路径 |

要求：

- 覆盖**全状态**：默认、空、加载、错误、超长内容、权限/未接入（如「磁盘未接入」「网盘离线」）。
- 同时给**桌面 1440×900** 与**移动 390×844**（若该界面两端都有）。
- 文案写最终稿，不写「标题1」「按钮A」这类占位。
- 能复用既有 `ui/` 基元的一律复用；需要新基元的，在 README 里单独列出并说明为什么现有基元不够。

### 从哪里改：Penpot 基线屏

> 设计文件：Penpot 上的 `Muse Video`（维护者账号私有，链接向维护者索取；结构与刷新方式见
> [`penpot-baseline.md`](penpot-baseline.md)）。

`Screens / HiFi（DOM 实测）` 里的 25 屏是**当前实现的镜像**（DOM 实测生成，详见
[`penpot-baseline.md`](penpot-baseline.md)）。改版从这个文件出发，**不另起画布重画**：

1. 在 Penpot 里复制受影响的基线屏，重命名为 `NN 描述（<slug>）`；基线屏本身**禁止手改**
2. 在副本上改布局、层级、状态；缺的状态就再复制一屏改出来
3. 把每个状态导出到 `docs/design/changes/<slug>/`（桌面 1440×900、移动 390×844）
4. 评审直接在 Penpot 里看：能点、能看实例、能量尺寸，对着导出的图逐条落结论

Penpot 只负责**结构、层级、状态、文案、区域划分**；像素细节（字重、字宽、行高渲染）
以代码为准 —— Penpot 没有 `Segoe UI`，替代字体必然有差，不要把字形争论带进评审。

## 2. 评审

评审对象是交互稿，不是实现。确认以下清单，逐条给结论：

- [ ] 信息层级：主操作是否唯一、是否在首屏
- [ ] 状态完整：空/加载/错误/边界是否都有稿
- [ ] 两端口径：桌面与移动的差异是否可解释（不是"顺手不一样"）
- [ ] 文案：用词与现有界面一致，没有未定义术语
- [ ] 组件复用：新基元的必要性成立，不会和 `ui/` 现有实现重复
- [ ] 可达性：键盘焦点顺序、对比度、点击区 ≥ 32px
- [ ] 与既有设计系统一致：颜色/圆角/间距取自 `docs/design/figma-tokens.json`，不引入新数值
- [ ] 已知问题排查：不把现有缺陷（如状态值未本地化、文案中英混排）当成设计沿用

没有 Penpot 访问权的贡献者：把每个状态的图放进 `docs/design/changes/<slug>/` 即可参与，
评审看的是图和 `README.md`，不需要打开设计文件。

评审结论写回 `README.md`：

```md
## 评审结论
- 日期：2026-11-26
- 结论：通过 / 驳回（附原因）
- 待办：[…]
```

## 3. 通过后才改代码

- 代码改动按交互稿实现；实现时发现稿子不可行（技术限制、需要新依赖、动到其他模块），
  **停下来回到第 1 步改稿**，而不是在代码里悄悄改布局。
- PR 描述必须链接该目录，并写一句「与交互稿的差异」——没有差异就写「无」。
- 稿子里被评审否掉的方案不要顺手实现。

## 4. 落地后回写，保持"稿 = 实现"

代码合并后：

1. 重跑 `frontend/scripts/capture-design.mjs` 刷新 `docs/design/screenshots/`；
2. 重跑 `frontend/scripts/dump-design-dom.mjs`，把受影响的屏按新 DOM 重导进 Penpot 基线
   （步骤见 [`penpot-baseline.md`](penpot-baseline.md)）——基线必须与代码同一版；
3. 变更副本屏移到基线旁边并标注 `<slug>` 与合并日期，作为决策记录保留；
4. 界面与稿子不一致时，以**代码 + 新截图**为准并更新稿，不留下两套"真相"。

## 例外

- **纯文案/颜色/图标替换**，不改布局结构、不增删元素：可跳过画稿，但 PR 必须说明「结构未变」。
- **缺陷修复**（布局错位、溢出、遮挡）：以复现截图 + 修复后截图代交互稿，评审即对比两张图。
- **内部重构**（不改变用户可见界面）：不需要交互稿，但要说明"用户可见差异为零"的依据。
