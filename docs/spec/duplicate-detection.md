# Muse 查重（同番号多版本）设计

**Status:** Implemented
**Scope:** 识别收藏中同一部作品被保存多个版本的情况，提供界面让用户选择保留哪一个版本
**Target:** 桌面端（Wails）+ 局域网移动端（共用 `api.Library` 门面）
**Version:** v1

---

## 1. 目标

刮削识别出番号后，收藏库中可能出现同一部作品的多份拷贝：同一部片子的不同清晰度、
不同压制组、带与不带字幕。它们各自是一条收藏记录（对应一个真实文件），但用户通常只
想留一份。

查重面板把这些作品成组列出，让用户二选一：

- **保留某一个版本**：把同一作品的其他版本从收藏中移除；
- **保留两者/全部**：等价于忽略这条重复提示，之后不再出现在列表中。

核心原则与收藏库一致：**查重只删除收藏记录与缩略图，绝不删除或移动源视频文件。**

## 2. 什么算重复

分组依据是 **番号 + 上下集标记**。

```text
abc-123.mp4          ┐
abc-123 1080p.mkv    ├─ 同一部作品，3 个版本 → 提示查重
ABC-123 BD 修复版.mp4 ┘

abc-123-1.mp4        ┐
abc-123-2.mp4        ┘─ 上下集，不同作品 → 不提示

abc-123 1080p.mp4    ┐
abc-123 4K.mkv       ┘─ 分辨率/画质后缀不是集数 → 两个版本，提示查重
```

规则细节（`backend/jav/extractor.go`）：

1. 上下集标记只认紧跟在番号后的**纯数字**，分隔符可以是 `-`、`_`、`.` 或空格：
   `abc-123-1`、`abc-123_2`、`abc-123.3`、`ABC-123 4`，前导零归一化（`-02` 与 `-2` 同集）。
2. 标记后面不能紧跟字母或数字，因此 `ABC-123-4K`、`ABC-123 1080p` 没有标记。
3. 标记后面不能是 `.数字`，因此 `abc-123 5.1ch.mkv` 是音轨布局而不是第 5 集。
4. `FC2-4894253-2` 这类 FC2 番号同样支持标记。
5. 文本形式的标记（`abc-123 part1`）**故意不识别**。误判成集数会把一部作品拆成两个
   幻影作品，真实的重复拷贝会被永久隐藏；反过来漏判只是面板上多出一条提示，用户点
   一下「保留两者」即可。两种错误的代价不对等，所以取保守的一侧。

番号本身由现有刮削流程提供（`video_jav.code`），因此查重结果与详情页显示的番号永远
一致，不需要单独的表来保存分组。

## 3. 忽略（保留两者）的语义

「保留两者」写入 `jav_duplicate_ignores`：

| 列 | 说明 |
| --- | --- |
| `dup_key` | 分组键（番号 + 标记），主键 |
| `video_ids` | 忽略时该分组成员 id 的升序列表（逗号分隔） |
| `created_at` | 忽略时间 |

忽略**针对的是那一组成员，而不是那个番号**。当成员集合发生变化（新增了一份拷贝，或
删除了一份），旧记录不再匹配，该作品会重新出现。这样新加入的文件不会静默继承一个旧
决定。所有拷贝都已删除时，忽略记录会被清掉，避免残留标记压掉将来无关的同番号分组。

## 4. 数据流

```text
video_jav.code ─┐
                ├─→ jav.Service.ListDuplicates()  ─→ 分组（番号 + 文件名标记）
videos.file_name┘         │
                          └─→ 与 jav_duplicate_ignores 比对 → Ignored 标记
```

- 读取在 `backend/jav/repository.go` 的 `ListDuplicateCandidates` 完成：一次 join 取回
  所有已识别番号的收藏（排除 `override_mode='skip'`）。
- 分组、标记判定与忽略匹配在 `backend/jav/service.go` 的 `ListDuplicates` 完成。
- 只有一个成员的组不返回（一份拷贝不算重复）。
- 排序：分组按其中最新的一份拷贝排序，与收藏库默认顺序一致。

## 5. API

门面（`backend/api/library.go`，桌面与 HTTP 共用）：

| 方法 | 说明 |
| --- | --- |
| `ListJavDuplicates(includeIgnored bool)` | 查重工作列表；`includeIgnored` 为 false 时隐藏已忽略的作品 |
| `IgnoreJavDuplicate(key string)` | 保留该组全部版本（忽略重复提示） |

HTTP（`backend/server/server.go`）：

| 端点 | 说明 |
| --- | --- |
| `GET /api/jav/duplicates[?includeIgnored=1]` | 查重工作列表 |
| `POST /api/jav/duplicates/ignore` | 保留全部版本，请求体为 `{"key": "..."}` |

Wails 绑定：`App.ListJavDuplicates`、`App.IgnoreJavDuplicate`。

移除版本复用既有入口 `RemoveVideo` / `DELETE /api/videos/{id}`，因此组归属清理、缩略图
删除、刮削记录删除的行为与从收藏库移除完全一致。

## 6. 界面

**桌面端**：侧边栏「刮削」分组下的「查重」入口（`DuplicateView.tsx`）。

- 每个作品一张卡片：番号、集数标记（如有）、版本数、已忽略标记；
- 每个版本一张小卡片，附带「保留此版本」按钮；
- 顶部「保留全部」/「保留两者」按钮；
- 「显示已忽略」开关，用于复查决定（例如仍想只留一份）；
- 面板自带关键字框（按番号或文件名筛选），因此整库搜索框在该视图下隐藏，不会出现
  一个看似可用却无效的输入框；
- 面板视图下卡片键盘导航（方向键 / Ctrl+A / Delete）保持关闭，避免作用到背后已加载
  的收藏网格。

### 6.1 版本卡片可交互（右键菜单）

版本卡片带与收藏库卡片**完全相同**的右键菜单（打开 / 查看详情 / 打开所在文件夹 /
复制路径 / 编辑信息 / 从收藏中移除 / 添加到分组），由同一个 `ContextMenu` 组件渲染，
因此行为不分叉。带来的工作流是：

```text
右键版本 → 打开所在文件夹 → 在文件管理器中删除该文件
        → 回到查重面板 → 该版本显示「⚠ 文件缺失」→ 对另一版本点「保留此版本」
        → 唯一剩下的记录就是文件仍在的那个
```

**为什么这样就绕过目录监控**：目录监控的扫描逻辑是「把目录树和当前收藏列表做差集」，
不在收藏里的文件会被重新导入。用户主动「从收藏中移除」时文件仍在磁盘上，所以下一次
扫描（5 分钟兜底周期，或该目录任何变动触发的重扫）会把它加回来。而**把文件本身删掉**
之后，扫描时它已经不在目录树中，自然不会被重新导入，决定就稳固了。查重本身**不提供
删除文件的能力**（全局原则：绝不触碰源文件），所以这个动作始终由用户在文件管理器中
完成。

「⚠ 文件缺失」标记是这个流程的确认手段，因此面板每次加载都会对列表中每个版本调用一次
`RefreshStatus`（本地 stat），而不是依赖库里可能已经过期的状态字段——文件是在应用之外
被删掉的，数据库并不知道。

**移动端**：底部第四个标签「查重」（`frontend/src/mobile/components/DuplicateView.tsx`），
逻辑与桌面一致，确认步骤使用 confirm sheet。卡片点击进入详情；桌面专属的「打开所在
文件夹 / 复制路径」在移动端不提供（作用于服务器文件系统，对手机无意义，见
`mobile-web-design.md` 的能力对照表）。

## 8. 非目标

- 不做基于时长、分辨率或文件哈希的自动判定：这些是「保留哪一个」的决策依据，不是
  「是否重复」的判据。番号是唯一可靠的作品身份。
- 不做自动删除：移除动作永远由用户点击触发。
- 不移动或删除源文件（全局原则，见 spec-v1.md §41）。
- 不做「批量全部保留一份」：每部作品的取舍需要人工判断。
- **不记录「已舍弃路径」以阻止目录监控重新导入**。用户按 6.1 的流程在文件管理器中删掉
  文件后，扫描自然不会再导入它；仅删收藏记录而保留文件的做法，5 分钟内会被目录监控
  重新加回来——这是目录监控的既有语义（监控目录里的视频本就会自动导入），不是查重的
  缺陷。若将来需要「忽略但保留文件」，应作为目录监控的能力单独设计（含撤销入口），
  而不是在查重里加一张排除表。
