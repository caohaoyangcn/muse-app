# 相似影片推荐（详情页底部）技术设计

**Status:** 已实现（打分内核 + 标题通道 + 两端展示）；标题 embedding 经实测否决，见 §4
**Scope:** 影片详情页底部增加「类似影片」推荐栏，综合系列、风格标签、演员、厂牌、发行时间与片名标题
**Target:** Windows/macOS Wails Desktop App + 局域网移动端
**Version:** v1

---

## 1. 目标与位置

详情页最底部增加一排可横向滚动的推荐卡，默认 8 张，每张带一条可读的推荐理由：

```text
视频详情
    |
    +-- 封面 / JavBus 元数据
    +-- 演员 / 标签
    +-- 刮削状态
    +-- 番号与刮削模式
    +-- 文件信息
    +-- 类似影片   <-- 新增
          卡片：封面 · 【番号】译名
          理由：同系列 / 同演员 / 相似标题 / 同厂牌 / 同年发行
```

硬约束：

- **推荐是读路径的副产品，不阻塞详情页首屏。** 详情页先用已有数据渲染，推荐栏独立取数、独立 loading。
- **不联网。** 整条链路只用本地已刮削的字段：没有模型下载、没有推理运行时、没有外部请求。
- **纯读。** 不写 `videos` / `video_jav`，唯一例外是 embedding 缓存表。
- **召回集永远排除**：影片自身、已删除/回收站条目、同一作品的其他副本（`jav_duplicate_ignores` 视为已处理）。

## 2. 信号与清洗

| 信号 | 来源 | 归一化规则 | 权重 |
| --- | --- | --- | --- |
| 演员 | `video_jav.actors_json`（经 `actor_aliases` 合并后的规范名） | 去空白、按规范名去重 | 0.28 |
| 风格标签 | `video_jav.tags_json` | 剔除「格式标签」后按 IDF 加权 | 0.24 |
| 系列 | `video_jav.series` + 番号前缀 | 全角转半角、去空格、小写 | 0.18 |
| 片名标题 | `video_jav.title`（刮削原文，永不用译名） | 字符二元组，剔除演员名/数字/样板词，见 §4 | 0.20 × (1−标签余弦) |
| 厂牌 | `video_jav.studio` | 小写、去空白 | 0.08 |
| 发行时间 | `video_jav.release_unix` | 指数衰减，见 §3.3 | 0.06 |

### 2.1 格式标签不是风格

标签里混着「拍摄/发行格式」，它们不描述内容，若参与相似度会让整个厂牌互相相似：

```text
單體作品 / HDTV / 高清 / 數位馬賽克 / 無碼破解 / LTX破解 / 獨占配信 / 生写真
```

第一版用**显式剔除列表**（`formatTags`）而不是靠 IDF 自动压低：它们在某些子集里 DF 可能并不高（例如「LTX破解」只出现在破码片里），IDF 压不住，反而会制造一个假的强维度。

### 2.2 有无码是硬分区

`is_uncensored` 不同的两部片不放进同一排推荐——破码/无码片与有码片混排会让整排看起来「不对」。「無碼破解」标签**不**参与这个判断：它描述的是本地这份文件被破解过，而不是作品本身有没有码。同侧候选不足 `limit` 时，用另一侧的候选静默补满（结果里不标记：排序与理由不变，只有入围者变了）。

## 3. 打分模型

三段式：召回 → 排序 → 多样性。

### 3.1 召回

召回读取的是**整库特征**，不是一次 SQL 并集：`Corpus` 必须先看到所有条目才能算出 IDF，几千条规模下一次全表读取（约 2–5 ms）比"先查候选再查统计"更简单也更快。真正的召回是评分前的一道闸门：

- 必须有内容信号重叠（演员 / 标签 / 系列 / 厂牌）；仅发行时间相近不算相似；
- 排除自身、同番号（`query.code == candidate.code`）、已删除与回收站条目；
- 有无码分区，同侧候选优先，不足 `limit` 时用另一侧补满；
- 候选规模由 `limit` 决定（默认 8、上限 40），不需要额外的固定截断。

### 3.2 各信号产出 [0,1]

```text
s_actor  = IDF 加权余弦(canonical actors)
s_tag    = IDF 加权余弦(style tags)
s_series = 1.0  同 series
         | 0.6  只有番号前缀相同（SSIS/SONE/IPZ…，视作作品线）
         | 0.0  否则
s_studio = 1.0 同 studio，否则 0
s_title  = IDF 加权余弦(稀有标题二元组)
s_time   = exp(-|Δdays| / 1095)
```

`Δdays` 用 1095 天（约 3 年）作时间常数：同年 = 1.0，±3 年 ≈ 0.37，±10 年 ≈ 0.04。时间只提供**轻微的「同年代制作风格」先验**，不允许压过演员或系列——一部 2007 年的片和 2024 年的片只要演员/标签对上，仍然应该排前面。

### 3.3 融合

```go
score = Σ(w_i · s_i)   // 缺失的信号贡献 0，不做分母归一
```

**不做权重重归一化。** 重归一化会把"只有厂牌相同"的影片放大成 1.0——厂牌是查询唯一可用的信号，它填满了整个分母——而这恰恰应该是最弱的匹配。缺失的信号是**丢失的证据**，不是中性的证据。

代价是绝对分数随数据完整度变化：里程碑 1 尚未接入标题通道，满分是 0.84（演员 + 标签 + 系列 + 厂牌 + 时间）；embedding 落地后自动回到 1.0，权重无需重调。分数只用于排序与测试，界面不展示。

### 3.4 多样性与保底

纯分数排序会出现「整排同一个演员」或「整排同一个系列」。排序末尾套一层 MMR：

```go
// λ = 0.7；similarity = max(标签余弦, 演员余弦)，系列重复交给上面的上限处理
next = argmax( λ·score(i) - (1-λ)·max_{j∈selected} sim(i, j) )
```

MMR 只在按分数截出的短名单（`8 × limit + 24` 条）上跑，不对全库做：推荐栏只有 8 个位置，在全库上做多样性是纯浪费。留下余量是为了在上限生效时仍有足够候选可挑。

再加两条上限（产品判断，不是可调参数）：

- 同一演员默认最多 4 张
- 同一系列默认最多 3 张（`series` 为空时退化为番号前缀）

上限是**排序偏好**而不是配额：达到上限的候选会被排到未达上限的候选之后；当整库都没有足够候选时，行尾仍会用它们补满，推荐栏不为凑数留空位。

### 3.5 理由

`Reasons []string` 由触发的信号生成，按贡献（`w·s`）降序，最多 2 条：

```text
同演员 · 同题材 · 同系列 · 同作品线 · 同关键词 · 同厂牌 · 同年发行
```

`同题材` 仅在标签余弦 ≥ 0.5 时给出；`同作品线` 指番号前缀相同而 `series` 不同（或缺失）；`同关键词：<短语>` 在标题余弦 ≥ 0.2 时给出，短语取自两个标题实际共有的最长片段（`sharedPhrase`），绝不引用打分没用上的文本；`同年发行` 按日历年份精确相等。前端只显示文字，不显示分数。

## 4. 标题通道（含 embedding 的实测否决）

### 4.1 为什么不是 embedding

第一版计划的是「片名 embedding」（独立配置、Migration v28、后台队列）。在真实库（2945 条刮削标题）上做完对照后否决了它。留下这段记录，是因为这个方案很容易被重新提出。

实测（200 个查询，真值 = 标签 + 演员 + 番号前缀；「剩余标签 J」只统计演员不同、前缀不同的对子，即标题通道唯一可能新增的那部分）：

| 变体 | 与内容 top10 重合 | 剩余标签 J |
| --- | --- | --- |
| 纯词面（Sudachi 分词 TF-IDF） | 0.303 | 0.213 |
| e5-small embedding（原始标题） | 0.254 | 0.202 |
| embedding（前缀+标题） | — | 0.204 |
| embedding（把标签写进嵌入文本） | — | 0.333 |
| 词面 + 演员/前缀词元 | 0.451 | 0.217 |

- **embedding 不含标签时没有独立信号**：剩余质量与纯词面持平。
- **把标签嵌进文本才跳到 0.333**——那不是语义发现了风格，是标签被重新编码，等于给 0.24 的标签通道再算一次。
- 余弦空间高度压缩（随机对 0.845 ± 0.024）：短标题上模型几乎没有区分度。

### 4.2 保留的那一层信号

标题里确实有**标签覆盖不到的细分题材**——厂商按卖点写进标题的营销句式（「杭打ち騎乗位」「共演」「絶対領域」「担任女教師」），比 42 个宽标签细。通道只取这一层：

```text
token    = 字符二元组（日语无词边界，不需要分词器、词典或 CGO）
剔除      = 演员名二元组（来自库内全部演员名）+ 数字 + 高 DF 样板词（DF > 3%）
权重      = IDF 加权余弦
有效权重  = 0.20 × (1 − 标签余弦)
理由      = 「同关键词：杭打ち騎乗位」
```

**权重校准**：第一版给 0.12，在真实库上一条「同关键词」都进不了前 8——因为「同厂牌 0.08 + 同年发行 0.06 = 0.14」已经压过了纯标题匹配，标题通道永远排不到位置。0.20 时它开始出现，且能压过「同作品线+同厂牌」的组合（实测 HND-136 → HND-354「真正中出し解禁」排第 1）。所以这个值不是审美选择，是通道能否生效的阈值。

三个剔除都有实测依据：演员名碎片制造最坏的假阳性（竹内あい / 竹内夏希 同姓不同人）；数字把「寝取られの館11」和「クラスメイト11人」连起来；样板词（ブルーレイディスク 等）在一个厂牌的整批片里重复出现。

高 DF 阈值是比例（3%），所以小库会退化成 `limit = 2`：两三部片的库里任意共享词都保留，但那时全库本来也互为「相似」。

### 4.3 参与规则

`title` 为空的收藏**不参与推荐**（查询与候选都是）：标题是这条通道唯一的文本。规则由 `jav.SimilarFeatures` 执行，打分层不判断。

**只用刮削原文，永远不用 `title_zh`**：译名是 LLM 派生物，用它匹配会把推荐绑定到翻译模型版本上。

### 4.4 成本

3000 条（平均约 15 个二元组）时，建语料 + 打分从 9.3 ms 升到 **17.7 ms**（`BenchmarkRankLibrary`），仍在 30 ms 目标内；无新依赖、无新表、无网络。

## 5. 接口

```go
// backend/api/library.go
type SimilarVideo struct {
    Video   video.Video `json:"video"`
    Score   float64     `json:"score"`
    Reasons []string    `json:"reasons"`
}

// SimilarVideos 返回与 videoID 相似的收藏，最多 limit 条（默认 8，上限 40）。
// 影片不存在、未刮削、库内过小时返回空切片而不是错误。
func (l *Library) SimilarVideos(videoID int64, limit int) ([]SimilarVideo, error)
```

桌面与局域网共用这一个门面（`api.Library` 是唯一业务入口）：

| 传输 | 形状 |
| --- | --- |
| Wails | `App.SimilarVideos(videoID, limit)` → 生成的 `frontend/wailsjs` 绑定 |
| HTTP | `GET /api/videos/{id}/similar?limit=N`；`limit` 缺失或非法时用默认条数，未知/未刮削收藏返回 200 + `[]` |

前端：

```text
views/similar/useSimilarVideos.ts   // 共享取数与状态（两端复用）
components/SimilarVideos.tsx        // 桌面：横向卡片排，末尾的独立 section
mobile/components/SimilarVideos.tsx // 移动：同一份数据，小一号卡片
```

- 取数走 `useLiveQuery(fetch, `similar:${videoId}:${limit}`)`：条数进查询键，换条数就是换一个问题。
- 读失败与首屏都归一成空数组：推荐是附属信息，不为它弹错误。
- `invalidate()` 后自然重读（刮削成功、译名更新）；分组变化不触发（分组不参与打分）。
- 卡片点击复用现有导航：桌面端 `openDetail` 开新标签页，移动端 `openVideo` 压栈；不新增路由。
- 封面统一走 `ui/CoverImage`，按框的方向选展示方式：竖版（3:4 海报，推荐栏与手机海报墙）右对齐裁切，只露封面——居中裁切会正好切在正封与封底的接缝上；横版（16:9 网格卡片、列表行与预览）等比收进框内，封面+封底完整可见。新的封面框只在这两种里选一种，不再各自决定裁切。

## 6. 性能与阈值

| 项 | 目标 |
| --- | --- |
| 单次 `SimilarVideos` 端到端 | < 30 ms（几千条库）；实测 3000 条时打分内核（建语料 + 排序 + MMR + 标题通道）**17.7 ms**，未含一次全表读取 |
| 常驻内存 | 标题二元组向量随语料构建，只在单次读取内存在，不跨请求缓存 |
| 详情页首屏 | 完全不受影响（推荐栏独立 loading） |
| 库规模上限 | 2 万条内暴力扫描；超过后单独立项 |

## 7. 校准

权重不是拍脑袋定的，用离线脚本校准（复用本次调研的 `_probe_title_similarity.py` 思路，落成 `scripts/eval-similar.py`）：

1. **代理真值**：以「同系列」与「同演员」为伪标签，计算推荐 top-8 的 hit rate / recall。
2. **对照**：逐项消融（去掉 title、去掉 series、去掉 time），确认每项都有正贡献；没有正贡献的项直接删掉。
3. **人工抽检**：随机 30 部片，人工标记 top-8 里「合理」的比例，目标 ≥ 70%。
4. **权重网格**：在代理真值上粗搜权重，再人工抽检确认没有被指标带偏（指标高但结果单调是常见陷阱）。

第一版权重就先按 §2 的表，等校准脚本跑通再调。

## 8. 测试

`backend/similar/scoring_test.go`（纯打分）

- 演员 > 系列 > 厂牌 的排序；只有发行时间相近不算相似
- 格式标签不构成相似；只有厂牌相同时分数恰为 0.08
- 排除同番号副本；未知 id → 空；有无码分区与回退
- 同一演员超过 4 张后排到其他候选之后，行仍补满
- MMR：等分时"新题材"排在"重复题材"之前；稀有标签权重更高
- `limit` 边界与空库

`backend/similar/title_test.go`（标题通道）

- 只共享营销短语、其余全不同的两部片互相推荐，并给出「同关键词」理由
- 标题里只有演员名（同姓不同人）→ 不推荐
- 一批蓝光片共享发行样板后缀 → 不推荐
- 标签已重合时标题通道不加分（分数在浮点误差内相同）
- 标题证据弱于演员证据（排序）
- 理由短语必须是两个标题都真实包含的片段

`backend/jav/similar_test.go`（读模型）

- 演员别名合并后只算一个人
- 回收站条目不出现；**无原始标题的收藏不参与**

`backend/api/similar_test.go`（门面）

- 排序 + 理由 + `【番号】` 读模型投影
- 排除同一作品的其他副本与已删除条目
- 演员合并生效前无推荐、生效后命中「同演员」
- 无刮削记录 / 无 jav 服务 → 空切片而不是 nil 或错误
- `limit` 夹取与未知 id

`backend/server/similar_test.go`（HTTP 路由）

- 与 Wails 绑定同形的行；未知收藏 → 200 + `[]`；`limit` 非法回落默认

前端（Vitest，`views/similar/useSimilarVideos.test.tsx`）

- 首屏给空数组而不是 `null`；读失败后仍是空数组
- 结果原样交给展示层；条数进查询键

## 9. 里程碑

1. **打分内核** —— ✅ `backend/similar` + `jav.SimilarFeatures` + `Library.SimilarVideos`。
2. **标题 embedding** —— ❌ 实测否决，理由见 §4.1；由标题词面通道（§4.2）替代。
3. **标题通道** —— ✅ 演员名/数字/样板词剔除、条件权重、`同关键词` 理由。
4. **前端与传输层** —— ✅ Wails 绑定 + `GET /api/videos/{id}/similar` + 共享 `useSimilarVideos` + 桌面/移动横排。

## 10. 未决问题

- **同系列保底槽位**：`series` / 番号前缀命中时是否给一个固定位置（用户一眼能懂的相关性），还没做。
- **时间权重是否要按厂牌区分**：老厂牌作品跨度大，时间先验可能有害；先全局一个常数。
- **标题通道的语言扩展**：通道只在日文原文上工作。若将来引入中文标题源（非译名），需要同一套二元组逻辑分别建 DF。
